# P4.3-MC — Préparation de la recette staging MC-G

Date de préparation : 16 octobre 2026.

**Statut : préparé, non exécuté. Aucun déploiement, aucune migration distante et aucune écriture staging ne sont autorisés par ce document.**

## 1. Préconditions bloquantes

- Le candidat P4.3-MC est gelé dans un commit identifié ; le SHA est inscrit
  dans le procès-verbal.
- Le verrou complet correspondant à ce même SHA est vert, sans skip.
- Le projet visé est bien **staging** ; son identifiant et son URL sont
  confirmés avant toute commande distante.
- Une sauvegarde staging et la preuve de restauration disponible sont
  conservées selon la procédure Phase 4.
- Les secrets Edge Function nécessaires sont configurés sans être affichés ni
  copiés dans les preuves ; `APP_REQUIRE_ADMIN_MFA=true` est vérifié.
- Les six profils distincts sont disponibles : visiteur, membre, éditeur,
  modérateur, administrateur et super-administrateur MFA.
- Les données de recette sont préfixées `RECETTE-P4.3-<horodatage>` et ne
  contiennent pas de données personnelles réelles.

## Point d'arrêt 2 — accord de déploiement staging

Obtenir un GO explicite avant les opérations distantes suivantes, dans cet
ordre : migrations staging, Edge Function `server`, puis frontend construit à
partir du SHA candidat. En cas d'échec, arrêter la séquence et documenter le
No-Go ; ne pas lancer de rollback destructif automatique.

## 2. Déploiement contrôlé à préparer après GO

1. Relever le SHA candidat et l'environnement ciblé dans le procès-verbal.
2. Vérifier le plan de migrations et la sauvegarde staging.
3. Appliquer les migrations approuvées sur staging.
4. Déployer l'Edge Function `server` du même SHA.
5. Déployer le frontend construit depuis le même SHA.
6. Vérifier `GET /functions/v1/server/api/health` : HTTP 200 et statut
   opérationnel.
7. Relever les versions déployées sans exposer de jeton, de clé ou de mot de
   passe.

Les commandes distantes existantes de référence se trouvent dans
`RECETTE_FINALE_PHASE4.md`, section 3. Elles ne doivent être exécutées qu'après
le GO ci-dessus et après contrôle de la cible staging.

## 4. Preuve et décision

Pour chaque cas, consigner : identifiant, SHA candidat, environnement, rôle,
préconditions, résultat attendu, résultat observé, date, recetteur et lien vers
une preuve expurgée. Ne pas inclure de jeton, clé `service_role`, mot de passe,
QR code MFA, code TOTP ni e-mail personnel non nécessaire.

**Go** uniquement si tous les cas applicables réussissent et qu'aucun incident
de confidentialité, d'autorisation, d'atomicité ou de migration n'est ouvert.
Sinon : **No-Go**, avec l'anomalie, son impact et le plan de correction ; le
candidat staging n'est pas promu.
