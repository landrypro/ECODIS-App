# ECODIS App — Correctif P4.2.2-B02 : renvoi d'invitation et erreurs e-mail

**Statut :** implémenté localement ; activation de l'envoi réel en attente d'un domaine expéditeur Resend vérifié  
**Périmètre :** `POST /users/:id/invitation`, interface `/admin/users`, Edge Function Supabase et livraison transactionnelle  
**Déclencheur :** le cas B-02 retourne un HTTP 500 générique lors du renvoi d'une invitation.

## 1. Constat vérifié

L'endpoint de renvoi appelle aujourd'hui `auth.admin.inviteUserByEmail` pour un utilisateur Auth déjà existant mais non confirmé. Toute erreur remontée par Supabase Auth est traitée par le gestionnaire générique et devient HTTP 500.

Les logs Auth staging montrent également des réponses `429: email rate limit exceeded` durant la séance de recette. Le navigateur ne peut pas distinguer ce cas d'une panne interne.

Le besoin B-02 reste valable : un administrateur autorisé doit pouvoir demander le renvoi d'une invitation non confirmée, sans mot de passe, lien, jeton ou secret affiché dans l'interface.

## 2. Décision d'architecture proposée

Le correctif est découpé en deux sous-lots indépendants.

| Sous-lot | But | Dépendance externe |
|---|---|---|
| B02.1 | Classer correctement les erreurs Supabase Auth et éliminer le faux HTTP 500. | Aucune |
| B02.2 | Produire et envoyer une nouvelle invitation à un compte en attente via un fournisseur transactionnel serveur. | Compte fournisseur, domaine expéditeur vérifié et secrets |

Le fournisseur recommandé est **Resend**, appelé par l'Edge Function Supabase via son API HTTP. La clé reste donc dans les secrets Supabase ; elle ne doit pas être ajoutée à Vercel ni au frontend. Une autre solution SMTP/API est acceptable si elle respecte l'interface décrite ci-dessous.

Le retour à la pratique actuelle consistant à supprimer puis recréer le compte invité est explicitement interdit : il risquerait de perdre les rôles, le statut, les audits ou les références métier du titulaire.

## 3. Règles fonctionnelles

1. Le renvoi n'est possible que pour un compte existant, non confirmé, non suspendu et non `super_admin`.
2. Seul un acteur disposant de `users_manage_basic_roles` peut demander le renvoi.
3. Un compte confirmé reçoit une réponse 409 invitant l'administrateur à utiliser la récupération de mot de passe.
4. Le même destinataire est limité à une invitation par fenêtre configurable ; le délai recommandé est **60 secondes** en staging et production.
5. Une erreur de quota, de fournisseur ou de délivrabilité ne produit jamais un HTTP 500 générique côté interface.
6. Un nouveau lien est généré uniquement côté Edge Function ; il n'est ni retourné par l'API, ni stocké en base, ni journalisé.
7. Le message administratif est neutre : il confirme la prise en compte ou indique un délai de réessai, sans exposer la réponse brute du fournisseur.

## 4. Contrats API corrigés

### 4.1 `POST /users/:id/invitation`

| Situation | HTTP | Réponse publique |
|---|---:|---|
| Envoi accepté | 202 | `{ accepted: true, message: "La demande d'invitation a été prise en compte." }` |
| Compte déjà confirmé | 409 | `{ error: "Ce compte est déjà confirmé. Utilisez le lien de réinitialisation." }` |
| Permission insuffisante | 401/403 | Réponse existante, sans détail sensible |
| Fenêtre anti-renvoi ou quota e-mail | 429 | `{ error: "L'envoi d'e-mail est temporairement limité. Réessayez plus tard.", retryAfterSeconds }` |
| Fournisseur e-mail absent/indisponible | 503 | `{ error: "Le service d'e-mail est temporairement indisponible. Réessayez plus tard." }` |
| Erreur inattendue | 500 | Message générique et `requestId` uniquement |

La réponse HTTP 429 porte aussi l'en-tête `Retry-After`. Le frontend affiche le délai et désactive le bouton pendant ce délai ; il ne doit pas déduire l'existence d'un compte hors de ce contexte administrateur autorisé.

### 4.2 Traduction des erreurs Auth — B02.1

Créer un adaptateur serveur `mapAuthDeliveryError(error)` qui reconnaît au minimum :

- limite d'envoi Supabase (`over_email_send_rate_limit`, `email rate limit exceeded`) → 429 ;
- utilisateur déjà confirmé/existant selon le contexte → 409 ;
- indisponibilité réseau ou fournisseur → 503 ;
- toute autre erreur inattendue → 500, journalisée avec le `requestId`.

Les messages bruts Supabase ne sont jamais retournés. Cette même traduction s'applique aux routes d'invitation et de récupération de mot de passe, afin d'éviter de nouveaux faux 500.

## 5. Livraison transactionnelle — B02.2

### 5.1 Port d'application

Introduire une interface serveur `InvitationDeliveryGateway` :

```ts
sendInvite(input: {
  recipientEmail: string;
  recipientName: string;
  actionLink: string;
  idempotencyKey: string;
}): Promise<{ accepted: true }>;
```

La route reste propriétaire de l'autorisation, du statut du compte, du quota, de la génération du lien et de l'audit. Le fournisseur ne reçoit que le nom, l'adresse cible et le lien d'action à envoyer.

### 5.2 Flux de renvoi

1. Contrôler l'acteur et charger la cible avec le client `service_role` côté Edge Function.
2. Refuser les cibles confirmées, suspendues ou interdites.
3. Contrôler le délai de renvoi durable.
4. Générer le lien avec `auth.admin.generateLink({ type: "invite", ... })` côté serveur.
5. Transmettre le lien directement au fournisseur via `InvitationDeliveryGateway`.
6. Retourner HTTP 202 sans lien et créer l'audit `user_invitation_resent` seulement après acceptation du fournisseur.
7. Effacer toutes les références en mémoire après la requête ; n'écrire le lien ni dans les logs ni dans la base.

Une vérification technique locale et staging de `generateLink` sur un compte invité non confirmé est obligatoire avant bascule. En cas d'incompatibilité Supabase, l'implémentation s'arrête et une décision spécifique Auth est requise ; aucun compte n'est supprimé/recréé automatiquement.

### 5.3 Configuration et secrets

Secrets Edge Function requis pour l'option Resend :

```text
APP_EMAIL_PROVIDER=resend
RESEND_API_KEY=re_...
APP_EMAIL_FROM=ECODIS <invitation@domaine-verifie.example>
APP_INVITATION_RESEND_COOLDOWN_SECONDS=60
```

Prérequis opérationnels : domaine expéditeur vérifié (SPF/DKIM), adresse `From` autorisée, quota compatible avec staging/production et boîte de réception de recette. `RESEND_API_KEY` n'est jamais défini en variable `VITE_*`, dans Git, dans Vercel ni dans les logs.

### 5.4 Gabarit e-mail

Le gabarit contient : le nom ECODIS, le nom de l'invité, une explication concise, le bouton vers `actionLink`, une date/expiration gérée par Supabase Auth et une consigne de support. Il ne contient ni rôle, ni mot de passe, ni secret MFA.

## 6. Persistance du délai et audit

Le délai ne peut pas reposer seulement sur la mémoire de l'Edge Function. B02.2 ajoute une table privée `invitation_delivery_attempts` accessible uniquement au backend, avec :

- identifiant de l'invité et type `invite` ;
- dernière demande, prochaine date autorisée et état technique minimal ;
- acteur demandeur et identifiant d'idempotence ;
- aucune adresse e-mail complète, aucun lien, jeton, mot de passe ou contenu e-mail.

RLS est activée, sans privilège `anon` ou `authenticated`. Le `service_role` est la seule voie d'accès. Une migration dédiée documentera l'index unique et la politique de rétention.

Événements d'audit :

| Événement | Moment | Métadonnées autorisées |
|---|---|---|
| `user_invitation_resent` | Acceptation du fournisseur | cible, domaine e-mail, acteur, contexte |
| `user_invitation_resend_throttled` | Refus 429 local ou fournisseur | cible, délai, acteur ; sans lien ni e-mail complet |
| `user_invitation_delivery_failed` | Indisponibilité technique | cible, catégorie d'erreur, `requestId` |

## 7. Expérience frontend

- Le bouton devient indisponible pendant l'envoi et pendant un `Retry-After` reçu.
- HTTP 202 affiche une confirmation neutre.
- HTTP 429 affiche le délai, sans proposer de contourner le quota.
- HTTP 409 propose « Envoyer un lien de mot de passe » lorsque le compte est confirmé.
- HTTP 503 indique une indisponibilité temporaire ; l'interface ne masque pas l'incident comme une réussite.
- Les réponses 500 conservent le `requestId` pour le support, jamais le détail brut du fournisseur.

## 8. Critères d'acceptation et recette

| Cas | Vérification | Résultat attendu |
|---|---|---|
| B02-01 | Simuler une limite Supabase e-mail. | HTTP 429, message neutre, `Retry-After`, aucun 500. |
| B02-02 | Cible non confirmée, fournisseur disponible. | HTTP 202, un e-mail reçu, audit `user_invitation_resent`, aucun lien dans Network/logs/audit. |
| B02-03 | Deux clics pendant la fenêtre configurée. | Un seul envoi ; second HTTP 429 et audit de limitation. |
| B02-04 | Compte confirmé. | HTTP 409 ; aucun e-mail d'invitation et aucune génération de lien. |
| B02-05 | Fournisseur absent ou erreur réseau simulée. | HTTP 503, audit technique sans secret, aucune réponse 500 masquée. |
| B02-06 | Utilisateur sans permission. | HTTP 401/403 ; aucune tentative de génération/envoi. |
| B02-07 | Inspection sécurité. | Aucune clé, URL d'action, adresse complète ou secret dans frontend, audit, traces ou table technique. |

## 9. Décisions nécessaires avant déploiement de l'envoi réel

1. Valider **Resend** comme fournisseur transactionnel, ou fournir un fournisseur SMTP/API équivalent.
2. Fournir un domaine expéditeur qui pourra être vérifié, puis créer les secrets uniquement dans Supabase staging.
3. Valider le délai par défaut de 60 secondes et la rétention des tentatives techniques (recommandée : 30 jours).
4. Autoriser la migration de la table privée et le redéploiement de l'Edge Function après les tests.

## 9.1 État d'implémentation

- B02.1 est implémenté : les routes d'invitation et de récupération traduisent les quotas e-mail en HTTP 429 avec `Retry-After`, et les indisponibilités en HTTP 503.
- B02.2 est implémenté mais désactivé par défaut : `POST /users/:id/invitation` génère le lien côté Edge Function puis délègue l'envoi à `InvitationDeliveryGateway`.
- Sans `APP_EMAIL_PROVIDER=resend`, `RESEND_API_KEY` et `APP_EMAIL_FROM`, le renvoi retourne volontairement HTTP 503, sans générer de lien ni écrire de tentative durable.
- La migration `20260824211722_phase4_invitation_delivery.sql` fournit le délai atomique, privé et persistant ; elle doit être appliquée avant tout déploiement de l'Edge Function.

## 10. Hors périmètre

- renvoi de mot de passe par un administrateur via le nouveau fournisseur ; le flux Supabase existant reste en place mais bénéficie de B02.1 ;
- stockage des e-mails ou liens envoyés ;
- envoi massif, relance automatique, listes de diffusion ou campagnes ;
- traitement des retours de délivrabilité par webhook, qui relève d'un lot ultérieur.
