## Contrat backend pour MC-D

| RPC | Paramètres obligatoires | Paramètres facultatifs |
|---|---|---|
| `moderate_comment_transaction` | `p_comment_id`, `p_actor_id`, `p_action`, `p_expected_version` | `p_reason`, `p_request_id` |
| `resolve_comment_report_transaction` | `p_report_id`, `p_actor_id`, `p_status`, `p_expected_version` | `p_note`, `p_request_id` |
| `create_comment_report_transaction` | `p_comment_id`, `p_actor_id`, `p_reason` | `p_detail`, `p_request_id` |

Chaque RPC retourne la ligne modifiée/créée avec sa version. Il s'agit d'un DTO interne, à mapper avant toute réponse HTTP. Actions commentaire : `hide`, `restore`, `delete`, `author_delete`. Le dernier cas exige que l'acteur soit l'auteur.

L'acteur doit provenir de la session vérifiée par le backend, jamais du JSON du navigateur. La base contrôle son existence, son statut de compte et les rôles persistés pour les actions de modération. Si un sujet utilisateur Auth est présent, il doit correspondre à l'acteur. Les contrôles de session/révocation/MFA restent à effectuer dans l'Edge Function : une clé service est une autorité privilégiée, pas une preuve de session utilisateur.

SQLSTATE `PT400` : entrée invalide ; `PT403` : acteur/droits refusés ; `PT404` : ressource absente/non publiée ; `PT409` : version, transition ou doublon. MC-D doit traduire ces erreurs sans exposer les diagnostics SQL. Le helper HTTP actuel générique ne suffit pas.

Les RPC publiques délèguent à `moderation_private` (schéma non exposé dans la configuration actuelle). Aucun accès `anon` ou `authenticated` n'est accordé. Les administrateurs de base peuvent toujours modifier les droits ou désactiver un trigger : l'immutabilité garantit les chemins applicatifs, pas une résistance au propriétaire de la base.

## Transactions et concurrence

Une décision verrouille le commentaire, vérifie la version et la transition, incrémente sa version, écrit son événement puis traite les signalements ouverts par ordre d'UUID. Chaque résolution automatique incrémente la version du signalement et écrit son événement corrélé. Tout échec annule l'ensemble.

Le classement individuel verrouille d'abord le commentaire puis le signalement. Un signalement déjà traité ou une version obsolète produit un conflit, sans événement supplémentaire.

La création d'un signalement verrouille le parent publié en SHARE puis le commentaire en UPDATE. Elle ne peut donc pas laisser un nouveau signalement ouvert après une suppression concurrente utilisant ces fonctions. La contrainte d'unicité existante reste en place. La restauration ne rouvre jamais les signalements ; les états supprimés sont terminaux.

Les privilèges des anciennes tables ne sont pas révoqués ici pour éviter une rupture intermédiaire.
