# P4.3-MC — Préparation du gel du candidat

Date de préparation : 16 octobre 2026. Branche visée : `codex/p4-3-mise-en-conformite`.

**Statut : exécuté après GO utilisateur le 16 octobre 2026. Aucun tag ni déploiement n'est créé par cette procédure.**

## Objectif

Créer un commit qui représente exactement le code passé par le verrou vert du
16 octobre 2026. Le dépôt contient aussi des changements antérieurs et des
artefacts hors lot : aucun `git add .`, commit global ou remise à zéro ne doit
être utilisé.

## Point d'arrêt 1 — accord de gel

Avant toute écriture Git, obtenir un GO explicite pour :

1. examiner les différences indexées, non indexées et non suivies ;
2. établir la liste finale des fichiers P4.3-MC ;
3. indexer uniquement cette liste ;
4. créer un seul commit candidat.

Un tag annoté, par exemple `P4.3-MC-rc1`, est une opération distincte et
requiert un accord explicite supplémentaire.

## Procédure préparée

| Étape | Vérification ou action | Condition de poursuite |
|---|---|---|
| F-01 | Relever `git status --short`, `git diff --cached --name-only`, `git diff --name-only` et les fichiers non suivis | Chaque fichier a un propriétaire et un lot identifiés |
| F-02 | Comparer la liste aux périmètres MC-B à MC-F et aux modifications préexistantes recensées en MC-A | Aucun fichier P4.2, secret, document personnel ou artefact hors lot n'est inclus par défaut |
| F-03 | Relire le diff des seuls fichiers retenus, y compris migrations et scripts de qualité | Le diff correspond exactement au code validé |
| F-04 | Indexer explicitement les seuls fichiers approuvés, puis exécuter `git diff --cached --check` | Aucun problème d'espacement ni ajout inattendu |
| F-05 | Créer le commit candidat avec un message décrit dans le journal de changement | Le SHA produit est relevé immédiatement |
| F-06 | Vérifier `git status --short` et `git show --stat --oneline HEAD` | Les changements hors lot restent présents mais ne sont pas dans le commit |
| F-07 | Si le candidat est modifié après le verrou vert, relancer le verrou complet | Aucun changement de code ou migration ne sépare le SHA et les preuves |

## Éléments à attester dans le manifeste candidat

- SHA du commit et branche ;
- liste des migrations, incluant `20261014194235_phase4_moderation_integrity.sql`
  et `20261016001106_phase4_edge_function_service_permissions.sql` ;
- commande et résultat du verrou vert ;
- versions Node/npm, Deno et Supabase CLI ;
- liste des fichiers inclus et des changements préexistants exclus ;
- absence de secrets, clés, codes MFA, captures personnelles ou dumps réels.

## Règle de suite

Après le gel, aucun changement fonctionnel, de migration, de dépendance ou de
contrat API n'est ajouté au candidat. Une correction ouvre un nouveau candidat
et impose une nouvelle exécution du verrou. MC-G peut alors être proposé, mais
son déploiement staging conserve son propre GO explicite.
