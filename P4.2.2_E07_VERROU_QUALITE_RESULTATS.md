## Préparation E-07 — distribution WSL explicitement ciblée

Le lanceur `scripts/Test-QualityGateLocal.ps1` ne dépend plus de la
distribution WSL par défaut, qui est `docker-desktop` sur ce poste et ne peut
pas exécuter les contrôles du projet. Il sélectionne `Ubuntu-24.04` lorsqu'elle
est présente, ignore les distributions commençant par `docker-` et exige un
choix explicite si plusieurs distributions Linux restent possibles.

Une surcharge reste disponible :

```powershell
.\scripts\Test-QualityGateLocal.ps1 -WslDistribution 'Ubuntu-24.04' -RunLocalDatabaseChecks
```

Cette commande est le verrou E-07 complet. Elle relance `npm ci`, tous les
contrôles frontend, le backend Deno, le cycle Supabase local et l'arrêt propre.
Elle exécute donc à nouveau `supabase db reset --local`.

### Réexécution E-07 — échec transitoire Supabase local

Une première exécution complète après cette préparation a validé les 11
contrôles Node, frontend et backend Deno. Le seul échec est survenu pendant
`Supabase local start`, avec le seul message `Starting database...`.

Le diagnostic a ensuite confirmé que le conteneur
`supabase_db_ecodis-app` atteignait bien l'état Docker `healthy` et que
`supabase status` était vert. Il s'agit d'une course entre le retour de
`supabase start` et la fin des healthchecks Docker, non d'un défaut de schéma
ou de migration.

Les essais ont confirmé que `supabase start` retourne de façon instable sous
WSL, y compris avec `--ignore-health-check`, alors que les contrôles de base
exécutés manuellement sont sains. Le verrou ne traite donc plus ce code de
sortie comme un contrôle autonome.

La cause identifiée est l'exécution de `supabase start` et de `supabase db
reset --local` dans deux sessions WSL distinctes. Le démarrage Docker initié
par la première session n'était pas toujours visible ou achevé lors de la
seconde, d'où `supabase start is not running` malgré une base saine en
exécution interactive.

Le cycle est maintenant regroupé dans `scripts/test-supabase-local-wsl.sh`,
exécuté dans **une seule session WSL** par le verrou. Il lance Supabase,
attend explicitement l'état Docker `healthy` de PostgreSQL (jusqu'à 100 s),
exécute `db reset --local`, le lint SQL et l'historique des migrations, puis
arrête l'environnement via un nettoyage garanti. Le reset reste le contrôle
faisant foi : il recrée la base, applique les migrations et échoue si
PostgreSQL n'est pas disponible.

Le verrou complet doit être rejoué avec cette version du lanceur.
